# UI/UX & codebase audit — August 2026

Full-repo audit (site, `tabbied` package, build scripts, e2e) plus a hands-on
browser pass over every main flow at desktop and mobile widths. Bugs judged
"obvious" were fixed in the same PR (listed first); everything else is
recorded here with file references. Template-site code (`app/template/`,
`components/template/`) was out of scope by request. The July 2026 review
(`codebase-review-2026-07.md`) was the baseline — nothing listed there as
fixed has regressed, and its "noted, not fixed" items are re-checked at the
end.

The second half of this document is a separate concern: what it would take to
make Tabbied a genuinely good tool *for AI agents* building websites, designs,
and videos.

## Fixed in this PR

### Site

1. **Share links didn't capture edits on bare visits (medium).** The
   state→URL sync effect returned early whenever the URL had no query params —
   and since it's the only thing that ever writes params, a session that
   started at a bare `/patterns/<slug>/` (bookmark, typed URL, external link)
   could never arm it. Every edit stayed out of the URL, and "Copy shareable
   link" copied a link that reproduced none of them, while the toast said
   "Link copied". Gallery cards append `?seed=0000`, which is why the main
   flow masked it. *Fix:* the bare URL is kept only while the state still
   matches what it implies; the first real edit starts syncing.
   (`components/edit-pattern-page/EditPattern.tsx`)
2. **Transparent custom palettes broke on 3- and 8-digit hex backgrounds
   (medium).** Applying a saved palette with "transparent background" appended
   `00` to the raw stored color — `#abc` became the invalid `#abc00`, the
   transparency switch showed off, and the broken value flowed into share
   URLs. *Fix:* normalize via `toOpaqueHex` first, as the manual toggle
   already did.
3. **404 page was the unbranded Next.js default.** Added `app/not-found.tsx`
   with the site header/footer and links back to the gallery and home.
4. **Toggling "transparent background" kept the applied palette chip
   highlighted** even though the colors had diverged — now marks the palette
   as custom like every other swatch edit.
5. **Copy bugs:** "collection of pattern" → "patterns" (HowItWorks), "Browse
   pattern" → "Browse patterns" (homepage section label), "1 designs" → "1
   design" (gallery count), "patterns or pattern to use" (site description in
   `app/layout.tsx` + footer), "using out platform" (BuiltBy), "Terms of
   Services" → "Terms of Service" (footer link + page title).
6. **Docs API table drift:** `coverRender` documented a `cropTop` field that
   no longer exists; `fit`'s default said "per pattern" but it is `'grid'`
   for every design. (`app/docs/react/page.tsx`)
7. **No robots.txt or sitemap.** Added `app/robots.ts` and `app/sitemap.ts`
   (static-export compatible): all pages, all 295 editor URLs, all template
   sites, with trailing-slash canonical URLs.

### Package (`packages/tabbied`)

8. **SVG export of a `fit:"cover"` pattern was silently wrong (high).** The
   measurement pass neutralizes transforms via a style injected into the
   shadow root — which can never match the host `<css-doodle>` element, where
   the cover fit puts its `translate(...) scale(s)`. Measured geometry came
   back scaled while every `getComputedStyle` px value (border widths, corner
   radii, pseudo-element sizes, shadow offsets, transform origins) stayed
   unscaled, so exports mixed the two silently — the exact "silently wrong"
   outcome the SVG invariant forbids. *Fix:* the host transform is inline-
   neutralized during measurement and restored inside the existing two-phase
   unwind; exports now come out at the render box's native resolution.
   Verified in-browser: a 400×300 host at scale 0.5 exports a clean 800×600
   SVG and the on-screen transform survives. (`src/core/svgExport.ts`)
9. **`reconcile()` never re-ran the grid snap (medium).** A config-driven
   grid change (`update({ cellSize })` / a `density` prop change) re-rendered
   with a new column count but kept the canvas snapped to the old one —
   fractional tracks, hairline seams, until the next container resize.
   *Fix:* one `applyGridSnap` call in the reconcile path; verified in-browser
   (41→14 columns re-snaps to whole 104px tracks). (`src/core/createPattern.ts`)
10. **`hydratePatterns()` could never re-hydrate after `destroy()`.** The
    WeakMap kept returning the dead controller, so the README's own
    teardown-and-rehydrate recipe left the page blank with no error. *Fix:*
    controllers now expose a public `destroyed` flag and hydrate re-creates
    dead entries. (`src/core/hydrate.ts`, `src/core/createPattern.ts`)
11. **A bare `frequency:` in `data-options` parsed to `0`** (`Number('')`),
    below every slider's minimum, instead of falling back to the authored
    default as the documented contract promises. (`src/core/hydrate.ts`)

### Build scripts / e2e / docs

12. **`svg-parity-sweep.mjs` always exited 0** — scripted callers read FAILs
    as success. Now sets a non-zero exit code like its sibling gates.
13. **Parity threshold drift:** the sweep was missing `stepramp: 0.02`, which
    `e2e/svg-export.spec.ts` has and CLAUDE.md says must stay in sync.
14. **No batch-13 design in the e2e parity list.** Added one per family the
    batch is built from — `bight` (linear+radial gradient mask), `bench`
    (pure clip-path), `mirrorblack` (the batch's only stepped-conic mask) —
    all swept locally first (0.28–0.59% vs the 1% budget; `gully` was
    rejected at 0.865% as too close to CI variance).
15. **llms-full.txt documented removed syntax:** `data-cover-render`
    advertised an `800x800+120` overscan form the parser no longer accepts —
    an agent following it would have its attribute silently dropped. Also
    fixed: the catalog described as carrying a per-design "default fit" (fit
    is global since #55) in llms.txt, the package README, and CLAUDE.md; the
    self-contradictory "grid (default for designs with a grid option)"; stale
    "222 designs" comments. (`scripts/generate-llms.mjs`)
16. **CLAUDE.md accuracy:** `defaultFitMode()` no longer exists (codegen
    re-implements only `supportsSvgExport()`); stale design counts (253 →
    295 where the claim is current, qualified where it was a point-in-time
    measurement).

## Known issues not fixed (recommendations)

Ordered roughly by user impact within each group.

### Site — functional

- **Nested interactive controls in palette chips (a11y, medium).**
  `PaletteChip.tsx:46-67`, `PaletteRow.tsx:69-94`, `GalleryChipShelf.tsx:75-117`
  render `<span role="button" tabIndex={0}>` delete/edit affordances *inside*
  a `<button>`. Invalid ARIA; screen-reader and keyboard behavior is
  browser-dependent. Restructure so the actions are siblings (or the row is a
  `div` with explicit keyboard handling).
- **Mobile renders the full 437-palette library eagerly.** The sticky gallery
  shelf (`GalleryChipShelf.tsx:44`) and the editor's mobile chip row
  (`EditPattern.tsx`, the `isMobile ? mergedChips : chipRows` branch) mount
  every chip — ~4–5k DOM nodes re-rendered on each editor state change.
  Desktop paginates (8/page) and the browser reveals incrementally; the
  mobile paths predate the library's growth. Virtualize or paginate.
- **Gallery search matches names only.** `SelectPattern.tsx:155-161` filters
  on `item.name`, so searching "arch" or "dots" finds nothing while the
  catalog's descriptions — written to make the set searchable — go unused.
  Add `description` to `GalleryItem` and match against it too.
- **Disabled "Download SVG" has no reachable explanation.** The reason lives
  in a `title` on a `disabled` button (desktop menu + mobile panel) — no
  tooltip in most browsers, unreachable by keyboard/AT. Render the item
  enabled-but-inert with the note inline, or use `aria-disabled` plus a
  visible hint.
- **`flushSync` warning in dev.** Interacting with the export dropdown logs
  React's "flushSync was called from inside a lifecycle method" — it comes
  from a dependency (Base UI is at `1.0.0-rc.0`), not project code. Re-check
  after upgrading Base UI to a stable release.
- **Dev-only: StrictMode double-consumes the gallery-navigation marker**
  (`EditPatternHeader.tsx:84-86`), so "Back to gallery" never `back()`s and
  scroll restore doesn't arm under `next dev`. Production is unaffected.
  Cache the consumed value in a ref/module variable.

### Site — metadata & structure

- **No Open Graph / Twitter / canonical metadata anywhere.** Shared links
  render bare. Add `metadataBase`, per-page `openGraph` (the editor pages
  could even carry a per-design OG image — see the agent section below),
  `twitter`, and `alternates.canonical`.
- **Heading hierarchy on marketing pages:** the homepage headline is a `<p>`
  (`Hero.tsx:27`); privacy/terms use `h3` as their page title; homepage
  sections jump to h3/h4. One `h1` per page, stepped levels below.
- **Dead code:** `components/ButtonSelectGroup/` is imported nowhere (the
  editor renders its own segmented control; the string `'ButtonSelectGroup'`
  in pattern JSON is unrelated). `EditPatternHeader.tsx:185` references a
  nonexistent `styles.label`.

### Package

- **`background-size: cover|contain` on `url()` image layers exports
  stretched, not rejected** (`svgExport.ts:956-966` + `:1160`,
  `preserveAspectRatio: 'none'`). Latent — no preset uses it — but a custom
  definition would get silent distortion instead of
  `SvgExportUnsupportedError`, against the fail-loud invariant. Throw (or
  warn) for image layers.
- **Transient seams during the resize debounce:** between ticks,
  `applyGridSnap` snaps the canvas to the *newly derived* grid while the old
  grid is still rendered (`createPattern.ts` resize path) — sub-pixel tracks
  for up to 180ms mid-drag. Snap against the rendered cols/rows instead.
- **Legacy-Safari reduced-motion observation:** `motionQuery.addEventListener`
  has no `addListener` fallback, so on Safari ≤13 a mid-session preference
  toggle is missed. Probably below the support floor; noting for completeness.
- (July, still open) `exportImage()` rejects before mount rather than
  awaiting readiness; gallery cards keep per-card timers once approached.

### Build scripts / generators

- **Batch generators don't validate `def.order` against their owned range**
  (e.g. `generate-batch13.mjs` writes `galleryOrder: def.order` unchecked).
  An out-of-range order writes a file the batch's own prune can't delete and
  another batch's generator *would*. One-line assert per def.
- **`pattern-lints.mjs` scans only `style`** — a custom `doodle` preamble
  carrying `filter:` or a conic background passes the cheap lints and is
  caught only by the browser sweep. Scanning `style + doodle` for
  `SVG_BANNED` costs nothing. (The `var(--color0)` check must stay
  style-only.)
- **`build-image-manifest.mjs` silently resolves basename collisions across
  image roots** (last scanned root wins). Latent today; a duplicate-key throw
  makes it loud.
- **`check-gallery-thumbnails.mjs`'s regex premise is unasserted** — a
  reformat of `galleryThumbnails.ts` (quoted keys, brace on its own line)
  would make entries invisible and the check would false-green. Cross-check
  the regex count against a brace-depth count and fail on disagreement.
- **`vercel-ignore-build.sh`'s single-commit fallback is dead code** — the
  two conditions (`HEAD^` resolves, `rev-list --count HEAD` == 1) are
  mutually exclusive, so the July optimization never fires. Safe direction
  (always builds), but either delete the branch or fix the base detection.
- **`e2e/templates.spec.ts:208`** — a stray trailing `page.goto` asserts
  nothing and can fail an otherwise filesystem-only test on a transient
  server error. Delete.
- **Stale header comments:** `validate-svg-batch13.mjs` says "300 designs"
  (it's 42); `svg-sweep.mjs`/`render-sweep.mjs`/`pattern-lints.mjs` say
  "shared by batches 11 and 12" (13 uses them too);
  `docs/grid-snapping.md`/`docs/svg-export.md` carry pre-batch-13 counts.

# Making Tabbied a first-class tool for AI agents

You tested with a coding agent and "only the catalog was used". That is the
expected outcome of the current design, and it's worth being precise about
why before adding anything.

## Why agents stop at the catalog

The agent-facing docs (llms.txt → llms-full.txt → catalog.json) are genuinely
good — better than most packages have. But three structural things limit what
an agent does with them:

1. **The catalog is the only *queryable* surface.** Everything else is prose.
   An agent deciding "which of 295 designs suits a fintech hero" has exactly
   one tool: substring-match the one-line descriptions. The descriptions are
   evocative ("the mass at the end of the arch that takes the thrust") but
   not *selectable-by* — they don't say geometric vs. organic, dense vs.
   sparse, calm vs. loud, dots vs. lines.
2. **Agents can't see the patterns.** There is no image anywhere in the
   pipeline — no thumbnail URL in the catalog, no preview endpoint. A
   multimodal agent choosing a design for a *visual* purpose is flying blind,
   so it picks by name, renders once in the user's app, and hopes.
3. **Everything requires the agent to already be building a JS app.** The
   only way to get pixels out of Tabbied is to run css-doodle in a browser.
   For the "creating designs" and "creating videos" use cases the agent
   often just wants *an asset* — an SVG or PNG at some size — and there is
   no path to one without wiring up a page first.

The recommendations below are ordered by leverage-per-effort.

## Tier 1 — quick wins (days)

### 1. Add tags and use-case metadata to the catalog

Extend each `patterns/*.json` (and codegen) with a few enumerated fields:

```jsonc
{
  "tags": ["geometric", "quarter-circles", "playful"],   // visual vocabulary
  "mood": ["bold", "playful"],                            // calm/bold/organic/technical…
  "density": "medium",                                    // sparse | medium | dense
  "goodFor": ["hero-background", "poster", "pattern-fill"]
}
```

A controlled vocabulary (document the allowed values in llms-full.txt) matters
more than richness — agents filter reliably on enums and unreliably on prose.
Authoring 295 × 4 fields is mechanical work an agent can draft and you can
spot-check. This single change turns "grep the descriptions" into an actual
query, and it improves the *site's* search too (which currently matches names
only).

### 2. Ship per-design preview images at stable URLs, listed in the catalog

Generate `public/previews/<slug>.webp` (one seed, authored palette, ~480px)
at build time — the repo already has everything needed
(`scripts/render-pattern.mjs` drives headless Chromium). Add
`"preview": "https://tabbied.com/previews/<slug>.webp"` to each catalog
entry. A multimodal agent can then *look at* its shortlist before committing,
which is the difference between "picked something plausible" and "picked the
right one". This also gives you OG images for the editor pages nearly for
free.

### 3. Ship the agent docs inside the npm package

The coding agent that used "only the catalog" almost certainly met Tabbied as
an npm dependency, where the catalog is the only agent-facing file. Add
`llms.txt` (the llms-full content) to the package `files` and an `AGENTS.md`
to the repo root and package — both pointing at the same content. Agents
read `node_modules/<pkg>/README.md` and repo-root agent files far more
reliably than they fetch URLs.

### 4. Document the editor's share-URL scheme in llms-full.txt

`/patterns/<slug>/?seed=…&palette=…&palette=…&<optionId>=…&aspectRatio=…` is
stable, validated, and now (after this PR) faithfully round-trips. Documenting
it lets an agent hand its user an "open this exact configuration in the
Tabbied editor" link — a human-in-the-loop escape hatch that costs you a
paragraph. It also lets agents *read* configs out of links users paste at
them.

### 5. Add a "recipes" section to llms-full.txt

Five short copy-paste blocks cover the questions agents actually have: hero
background (absolute-positioned behind content), section divider, card
texture with a transparent background, full-bleed banner with `cover`,
static-HTML embed via `hydratePatterns`. Each is three lines of context the
model would otherwise have to infer, and wrong inference here (the
definite-height gotcha) is the main way generated code fails today.

## Tier 2 — the render path (a week or two)

### 6. A headless render CLI: `npx tabbied render`

```bash
npx tabbied render radius --seed k9Pz --palette "#0B1020,#3E8BFF" \
  --size 1600x900 --out hero.svg        # or .png
```

This is the single biggest unlock for the "designs" and "videos" use cases:
it turns Tabbied from "a component you integrate" into "a generator you
call", usable from any language, any build pipeline, any agent sandbox with
Node. The machinery exists in `scripts/render-pattern.mjs` and the SVG
converter already runs headless; the work is packaging it (playwright-core
as an optional/peer dep, or `--browser <path>`), arg parsing, and docs. Ship
it as a `bin` in the existing package so `npx tabbied` just works.

### 7. Frame sequences for video

Once the CLI exists, `--frames 90 --reseed-every 30` emitting
`frame-0001.png…` makes Tabbied consumable by ffmpeg/Remotion pipelines. The
morph between seeds is Tabbied's signature motion; a deterministic
seed-per-frame contract (document that seed N+1's transition is a CSS
transition you sample at intervals, or simply cut) is what video tools need.
A `@remotion/tabbied`-style example in the docs — `useCurrentFrame()` →
`seed={seeds[Math.floor(frame / 30)]}` — would cover most agent video
requests without you building a real renderer.

### 8. A render endpoint (optional, infra-dependent)

`GET tabbied.com/render/<slug>.svg?seed=&palette=` would let no-code agents
(and `<img>` tags anywhere) use Tabbied with zero install. The site is a
static export, so this needs a worker (Cloudflare Worker running the SVG
converter against a headless render, or pre-rendered parameter subsets). Do
this only if you see demand from non-JS agents; the CLI covers most of it.

## Tier 3 — protocol-level integration

### 9. An MCP server

A small `tabbied-mcp` (stdio, shipped in the package or standalone) exposing:

- `search_designs(query, tags?, mood?, density?)` → catalog entries
- `get_design(slug)` → full entry + usage snippet
- `preview_design(slug, palette?, seed?)` → PNG image content (agents see it)
- `render(slug, config, format, size)` → SVG/PNG file

This makes design selection *interactive* — an agent in Claude Code, Cursor,
or any MCP client can look at five candidates, show the user, and iterate on
palette/seed before writing a line of integration code. Items 1, 2, and 6 are
prerequisites (the tools are thin wrappers over tags + preview + CLI), which
is why they come first.

### 10. A Claude Code skill / plugin

A `tabbied` skill file (the recipes from item 5 plus decision guidance:
when to use `grid` vs `cover`, palette-from-brand-color heuristics, the
SVG-export tiers) that users drop into their repos, or a published plugin.
Cheap to make from the llms-full content; meets agents in the harness they
already run in.

## What I'd explicitly *not* do

- **Don't add a JS-free SVG generator.** The catalog deliberately omits
  css-doodle `code`, and reimplementing css-doodle's semantics outside the
  browser would be a permanent correctness tax. The headless CLI gets the
  same result using the real renderer.
- **Don't auto-generate richer prose descriptions.** The one-liners are
  good; enum tags (item 1) are the machine-facing complement. Two prose
  fields would drift; enums won't.

## Sequencing

1 → 2 → 3 → 4/5 are independent and each useful alone; do them in any order.
6 unlocks 7 and most of 9. If you only do three things: **tags (1), preview
URLs (2), and the render CLI (6)** — after those, an agent can *choose* a
design, *verify* the choice visually, and *use* it in any medium without
having Tabbied's site in context at all.
